CONFIRMED FAILURE AND REPRODUCTION

User diagnostic 6c3588a267a4 reports release 3.5.4, Python 3.11.13, SQLite
3.34.1, and FOREIGN KEY constraint failed at DELETE FROM opportunities in
opportunity_reset.reset_once. Store construction has already passed the
opportunity-schema initialization call at that point.

A private reproduction retained an archived builder row with a foreign key to
opportunities(id). The original v3.5.4 physical reset raised the same exception
and rolled back, leaving its opportunity records and no completion marker.
This demonstrates the failure class; the supplied traceback does not identify
the specific child table in the actual hosting database.

REPAIR DESIGN VERIFIED

- The pending reset retires a fixed cohort using indexed membership. It does
  not delete or update the original five data groups involved in the failed
  reset: opportunities, assignments, deadline events, builders and opportunity
  notifications. Original activity/contribution history remains available.
- The old opportunities-owner-reset-v351 completion key is retained. A
  completed older reset preserves later imports; the reset runs only once.
- Verified private backups precede the reset and any required compatibility
  migration. Reset membership, generation, System summary and marker commit
  together. Backup failure and late write failure leave the prior state intact.
- The global reset summary uses its own history table, avoiding empty project
  IDs or synthetic user IDs in legacy foreign-key-constrained activity tables.
- The active register, status totals, search, team/user filters, team counts,
  unassigned count, detail/mutation paths, exports and deadline sweep all honor
  retirement membership. Old detail URLs are rejected, including for admins.
- The notification list, total, unread badge and read operations use the same
  visibility rule, covering recorded notice IDs and retired target parents.
  Tender reminders and ordinary deletion notices retain their normal behavior.
- Reimport of the cleared workbook creates new UUID records. Old physical IDs
  remain reserved. Ordinary deleted records retain replay protection, and a
  stale workbook preview is rejected after the generation changes.
- Legitimate builder reuse restores its suggestion transactionally. An
  unsuccessful save rolls that reactivation back. Original builder rows remain
  unchanged; builder names from existing Tenders/Estimator projects still work.
- Actual metadata determines whether a supported activity/assignment table
  needs compatibility migration. Its entire original table is preserved under
  a unique archive name, known columns and IDs are copied exactly, and the
  original FK relationships/extra metadata/triggers/indexes stay on the archive.
  Activity sequence high-water marks are preserved. Canonical tables receive
  their own indexes, including when the original index names remain occupied.
- Normal writes change only assignment differences. Unchanged assignment
  records survive edits, approvals, expiry and ordinary deletions.

LEGACY RELATIONSHIP TESTS

Private fixtures exercise incoming foreign keys on all five formerly deleted
record groups, composite assignment references, RESTRICT and CASCADE actions,
archived builders referencing opportunities, and triggers that reject any
UPDATE or DELETE of historical rows. Reset succeeds while those originals
remain unchanged and foreign-key enforcement remains on.

Additional supported legacy schemas contain activity foreign keys to project
and actor tables, required extra activity fields, historical assignment
references, existing views/indexes/triggers, occupied archive names and older
activity sequence values. Tests verify actual region update, Excel import,
System expiry and assignment-edit behavior after migration, plus transactional
rollback on a late copy failure.

RETIREMENT QUERY CHECK

The disposable SQLite 3.34.1 fixture contained 10,000 retired opportunity rows
with substantial retained JSON bodies and 25 active rows. The production
list query returned exactly 25 active records. An instrumented result
projection observed zero retired JSON bodies; the ordinary query returned the
same result. EXPLAIN QUERY PLAN used opportunity_updated for candidates and
the composite (kind,record_key) retirement primary-key index for membership.

The single local query took 17.79 ms. This is advisory fixture evidence, not a
production latency/load guarantee. Candidate metadata still needs examination;
this check does not claim zero underlying page reads. The default ordering
uses a temporary B-tree. Filtering and pagination occur in SQL before records
are returned to the application.

LIMITS AND LIVE VERIFICATION

The production database and its complete historical DDL were not supplied.
The repair covers the confirmed reset failure class and the tested supported
activity/assignment layouts. It does not infer or silently discard arbitrary
additional constraints, corrupt rows or unrelated custom schema definitions.
A genuine storage, backup, permission or unsupported-schema failure still
stops safely and is available through the existing admin diagnostics route.

The old records are cleared from the active workspace, not physically erased
from all storage. Retention is intentional: it protects linked records and the
requested historical contribution/audit record. Backups and archive tables
must remain available for recovery and historical references.

The live installation is confirmed only after upload and restart when:
  https://tec-const.ampecportal.com/api/health?check=tenders
returns release 3.5.5, schema 31 and all four checks as ok. Follow
UPDATE_INSTRUCTIONS_V3.5.5.txt for the exact installation and verification steps.
