WHAT v3.5.5 CHANGES

1. The pending clear retires a fixed cohort from the active register instead
   of physically deleting the original opportunity records or related rows.
   It preserves opportunity, assignment, deadline-event, builder, notification
   and activity history needed by existing relationships. A dedicated indexed
   table records which records belong to the cleared cohort.

2. The register, status sections, search, team lists/counts, exports, old detail
   URLs and deadline processing all exclude those retired opportunities.
   There is no additional Deleted section in the interface.

3. The inbox uses the same visibility rule for its items, total, unread badge
   and read actions. Old opportunity notifications are hidden. A later notice
   targeting a retired opportunity is hidden as well. Existing Tender reminder
   notifications continue to work normally.

4. A workbook containing the cleared projects can be imported again. Each new
   record receives a fresh UUID that cannot overwrite a retained old record.
   Ordinary individual deletions still have their existing replay protection.
   A preview made before the clear is rejected and must be regenerated.

5. Old opportunity-only builder suggestions are hidden. Selecting the same
   builder for new work restores that suggestion without changing its old row.
   Builders also supplied by existing Tenders or Estimator clients remain valid
   suggestions from those unaffected records.

6. Actual schema metadata is checked for additional activity and assignment
   constraints that would obstruct normal writes. When a supported legacy
   table has those constraints, its entire original table is retained in a
   permanent archive, and its known data is copied into the current writable
   application layout. Activity IDs and the existing sequence are retained.
   Original extra fields, foreign-key dependents, triggers and indexes remain
   on the archived original. Current tables receive their own indexes.

   This specifically covers legacy activity foreign keys or unsupported
   required metadata, and legacy assignment foreign keys/history references
   or unsupported required metadata. It prevents those constraints from
   breaking Excel import summaries, region updates, System expiry activity
   and assignment changes after startup has succeeded.

7. Edits, approvals and deadline processing update only assignment differences.
   An unchanged assignment is no longer deleted and inserted again.

8. User contribution reports continue to include original user activity and
   new opportunity actions. The register-wide clear has its own durable System
   summary and completion metadata, without inventing a user or project for
   the audit record.

THE CLEAR HAPPENS ONCE

The completion key is unchanged:

  opportunities-owner-reset-v351

If the earlier clear failed, v3.5.5 finishes it after schema initialization.
If that key already exists from a successful clear, the reset is skipped.
Later starts and future imports do not clear the new work again. Do not remove
this key to try to repair an error.

The reset records the previously visible opportunity count separately from
the total retained cohort, which can also include previously deleted records.
The membership, generation increment, System summary and completion marker
commit in one transaction. A failure rolls back that reset transaction.

BACKUPS AND RETAINED HISTORY

Before a populated clear, the application creates and verifies a private,
portable snapshot of the Tender database. A required compatibility migration
also takes its verified snapshot before changing the schema. These operations
use the existing process locks and write transactions.

For this host the snapshots are stored in:

  /home/ampecportal/tec-const.ampecportal.com/data/upgrade_backups/

The existing snapshot naming series are retained:

  tec_tenders-before-opportunity-schema-v354-<timestamp>-<suffix>.db
  tec_tenders-before-opportunity-reset-v351-<timestamp>-<suffix>.db

The older version tokens identify the migration/reset series. A new v3.5.5
snapshot can legitimately have one of these filenames.

Supported constrained tables are retained under names such as:

  opportunity_builders_legacy_v354
  opportunity_activity_legacy_v355
  opportunity_people_legacy_v355

A numbered suffix is used if an archive name is already occupied. A standard
compatible table is not archived just because the application is restarting.
Keep these archives and the backup files: other historical records can still
reference the archived tables. The active clear does not erase audit history.
