WHAT THE BUILDER MIGRATION PRESERVES

The supported legacy table has a name column and lacks builder_key. The
migration preserves that entire original table inside the Tender database,
normally under this name:

  opportunity_builders_legacy_v354

If that archive name already exists, a numbered suffix is used without
overwriting the earlier archive. Original spellings, extra columns, historical
references and unsuitable name values remain with the archived table.

A new active builder directory uses the current builder_key/name structure.
Usable names are cleaned with the application's existing builder rules. Names
that produce the same normalized builder key share one suggestion; a stable
source ordering selects its display name. Invalid, empty or nontext values
remain preserved in the archive and are omitted from active suggestions.
Opportunity records and contribution/audit history are retained by this
conversion. Current application writes use the new active directory.

Before converting a legacy builder table, the application makes a verified
snapshot of the entire Tender database, including when the opportunity
register is empty or its table has not yet been created. The snapshot is
stored beside the runtime Tender database under:

  upgrade_backups/
  <database-stem>-before-opportunity-schema-v354-<timestamp>-<suffix>.db

For the supplied runtime database location, the backup folder is:

  /home/ampecportal/tec-const.ampecportal.com/data/upgrade_backups/

The backup verifies the existing opportunity and builder row counts where
those tables exist, uses owner-only file permissions, and is a portable SQLite
file independent of a separate WAL file. Keep the backup and the archived
table for recovery.

The builder conversion, any missing opportunity columns, lookup recovery and
index creation share the existing opportunity-schema transaction and process
lock. A failure rolls back that migration transaction; a completed safety
backup remains available. Reopening the current schema does not repeat the
builder conversion or create another archive.

VERIFY THE RUNNING APPLICATION

Open:

  https://tec-const.ampecportal.com/api/health?check=tenders

Require HTTP 200 and the following values:

  {
    "success": true,
    "status": "ok",
    "release": "3.5.4",
    "schema_version": 31,
    "checks": {
      "tenders": "ok",
      "opportunities": "ok",
      "timezones": "ok",
      "sqlite": "ok"
    }
  }

This request exercises Tender startup, the opportunity schema and the actual
serving runtime. A plain /api/health request without check=tenders is not a
substitute. A version check from the terminal describes files on disk; the
deep health response identifies the application serving the request.

Then sign in and open Tenders > Opportunities. Check the expected register
and the builder suggestions when adding or editing an opportunity. If you
import a workbook, review the import preview before confirming the import.

as an administrator, open the diagnostic for that exact reference:

  https://tec-const.ampecportal.com/api/admin/startup-diagnostics?reference=<error_reference-from-the-new-failed-request>

Replace the angle-bracketed text with the complete 12-character reference in
the new error response. The latest saved diagnostic can also be retrieved at:

  https://tec-const.ampecportal.com/api/admin/startup-diagnostics

Check its reference, created_at, release and runtime before treating it as a
current failure. A saved v3.5.3 diagnostic can remain available after a
successful v3.5.4 repair. Diagnostic history does not replace the live health
check, and an older worker PID is not the expected PID after restart.

If the health response still reports v3.5.3, the request has not reached a
worker serving the updated release. Confirm the files were copied into the
existing app root and restart the existing application in cPanel. A failed
deployment step does not automatically roll back already uploaded files.
