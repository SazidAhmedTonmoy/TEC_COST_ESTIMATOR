TEC ConEst v3.5.3 — Repair the confirmed Opportunities schema failure
Prepared 21 October 2026

CONFIRMED CAUSE

The administrator diagnostic with reference 84852851964d reported:

  sqlite3.OperationalError: no such column: deleted_at
  conest_app/opportunities.py, initialize(), while creating indexes

An older opportunities table already exists in the hosted Tender database.
CREATE TABLE IF NOT EXISTS leaves that table unchanged, so the old startup
code tried to index a column that the existing table did not contain. A fresh
local database receives the new column when its table is created. This explains
how the same code can open a new local database and fail on a retained server
database. The error was reproduced from the delivered v3.5.2 archive.

The diagnostic also reports a separate runtime mismatch: the actual Passenger
worker is /usr/bin/python3.9, version 3.9.25. This application's runtime checks
require Python 3.10 or newer. Configure the existing hosted application to use
Python 3.11, matching the version configured in the deployment workflow.

WHAT THIS UPDATE DOES

The application inspects the real opportunity table before creating indexes.
It upgrades supported id/body tables by adding missing current columns and
recovering their values from the stored opportunity JSON. Existing JSON,
existing SQL values, soft-deletion state and audit history are retained. It
reconstructs missing lookup tables from stored records only where necessary.
It does not invent past approval events or notifications.

For a populated legacy register, a verified SQLite snapshot precedes schema
changes. The migration and index creation share one transaction, and an OS
lock coordinates Passenger workers. If the backup or migration fails, the
opportunity schema transaction is rolled back and startup remains unready.
Repeated startup with the current schema does not repeat the migration backup.

The schema snapshot is stored beside the runtime Tender database under:

  upgrade_backups/
  <database-stem>-before-opportunity-schema-v353-<timestamp>-<suffix>.db

For the runtime path supplied in the diagnostic, this folder is:

  /home/ampecportal/tec-const.ampecportal.com/data/upgrade_backups/

The snapshot includes the Tender database at the time it was made. It is a
portable SQLite file and does not depend on a separate WAL file. A failure
later in the migration leaves that safety snapshot available.

The installer now checks an explicitly selected production interpreter before
running pip. Missing configured paths and shell-only guesses fail with clear
messages. Python and SQLite support are checked before installation; package
imports and NSW/VIC timezone data are checked afterward. CONEST_PYTHON selects
command-line tools only and does not change Passenger's configuration.

INSTALL THE UPDATE

1. Use TEC_COST_ESTIMATOR_v3.5.3_CHANGED_FILES.zip over the previously delivered
   v3.5.2 application. Use TEC_COST_ESTIMATOR_v3.5.3_FULL.zip for a complete code
   update or if your code is not at that baseline. Both ZIPs contain the
   TEC_COST_ESTIMATOR/ top-level folder. Copy that folder's CONTENTS into the
   existing app root, preserving the paths beneath it:

   /home/ampecportal/tec-const.ampecportal.com/

   Do not create another nested TEC_COST_ESTIMATOR folder in the live app.

2. Keep the live data directory, databases, uploads, environment and hosting
   configuration. Runtime databases are excluded from both packages. For a
   manual full-code upload, preserve the server's existing passenger_wsgi.py
   interpreter configuration and .htaccess settings. This update changes
   neither of those files. GitHub deployment already preserves them.

3. Correct the application's Python selection using the section below. Do this
   before rerunning the automated deployment so its installer uses the same
   Python as Passenger. Installing Python 3.11 somewhere on the server or
   selecting it on the GitHub runner does not switch an existing web app.

4. Install requirements.txt in the selected application environment. There is
   no new Python dependency in v3.5.3. The existing workflow runs:

   sh tools/install_runtime.sh

   For a manual update, use that command from the app root once its configured
   interpreter can be detected. The installer does not initialize a database
   from the SSH shell; the actual restarted application upgrades its runtime
   database.

5. Restart the existing app in cPanel. The GitHub workflow already requests a
   Passenger restart. To request the same restart manually from the app root:

   mkdir -p tmp
   touch tmp/restart.txt

6. Open the deep health URL shown below, then sign in and open Tenders. The
   first successful startup performs any required schema migration and the
   previously requested opportunity reset if that reset is still pending.

SELECT PYTHON FOR THE EXISTING HOSTED APPLICATION

If cPanel offers Software > Setup Python App:

  Open the existing application for tec-const.ampecportal.com. Select Python
  3.11, save the application settings, install requirements.txt in the newly
  selected application environment and restart it. Keep its current app root,
  startup file and application callable. Preserve the hosting tool's generated
  interpreter configuration. If 3.11 is unavailable, ask the provider to enable
  it for this existing application.

If the account only offers Application Manager:

  Ask the provider to configure this application to use a Python 3.11 virtual
  environment and provide its exact interpreter path. Do not guess that path.
  Existing Passenger applications can retain an older interpreter even after
  newer Python versions are installed on the server.

  cPanel also documents an INTERP/os.execl startup method. A provider can place
  the following block in the existing passenger_wsgi.py, using the VERIFIED
  full path to this application's Python 3.11 environment:

  import os
  import sys
  INTERP = '/REPLACE/WITH/VERIFIED/APP/ENVIRONMENT/bin/python'
  if sys.executable != INTERP:
      os.execl(INTERP, INTERP, *sys.argv)

  Verify the chosen interpreter directly before applying this block; it must
  report the intended application environment and Python 3.11. Keep any
  "from __future__ import annotations" line at the beginning of the file. Put
  the interpreter block after that line and before application imports, and
  preserve the rest of the existing startup code and application callable.
  Do not copy the placeholder path as if it were a real environment.

  The installer recognizes this literal startup selection. The GitHub workflow
  preserves passenger_wsgi.py, so the selection also survives later uploads.

For a one-off manual installer invocation, CONEST_PYTHON can point to that same
verified application interpreter. A terminal export or a cPanel web-app
environment variable is not guaranteed to reach GitHub's later SSH command.
Use the durable hosting/startup selection for future automated deployments.

VERIFY THE LIVE RESULT

Open:

  https://tec-const.ampecportal.com/api/health?check=tenders

The response must return HTTP 200 and include:

  {
    "success": true,
    "status": "ok",
    "schema_version": 31,
    "release": "3.5.3",
    "checks": {
      "tenders": "ok",
      "opportunities": "ok",
      "timezones": "ok",
      "sqlite": "ok"
    }
  }

Then sign in, open Tenders > Opportunities, and check the expected register.
The health endpoint checks the actual running worker and runtime database. A
plain /api/health response without check=tenders does not exercise this repair.

If a new failure remains, sign in as an administrator and open:

  https://tec-const.ampecportal.com/api/admin/startup-diagnostics

Use the new failure reference and created_at time. This endpoint can still
show an older saved exception after a successful repair; it is a diagnostic
history endpoint, not the health indicator. Retrieve the reference returned by
the new failed request when troubleshooting:

  /api/admin/startup-diagnostics?reference=<new-12-character-reference>

The current unsupported Python 3.9 configuration must be corrected even after
the deleted_at migration succeeds. The deep health guard intentionally rejects
that runtime. A failed deployment verification does not automatically roll
back files that the workflow has already uploaded.

THE PREVIOUSLY REQUESTED OPPORTUNITY CLEAR

The owner-requested reset still uses opportunities-owner-reset-v351. This
release does not create a new clear/reset marker.

If that reset has not completed, normal successful startup makes its separate
verified reset backup and clears the old opportunity register, assignments,
builder suggestions, deadline events and opportunity notifications. Tender
submissions, reminders, account/team data and contribution history remain.

If the reset already completed, later imported and manually added projects
remain on subsequent startups. The schema migration itself preserves records.
The packaged opportunity seed remains empty. Both migration and reset backups
can exist for the same first successful upgrade; keep them for recovery.

EXCEL IMPORT TEMPLATE

It is also available from Download template in the import dialog. Enter one
opportunity per row, select NSW or VIC, list multiple builders on separate

review the preview before importing. NSW uses 63-79 Parramatta Rd Silverwater,

kilometres is a supplied value and is not automatically calculated by routing.

LIVE STATUS AND SCOPE

The code and release archives were prepared and tested with private database
fixtures. No production deployment, production file edit or production data
deletion was performed while preparing this package. Only the supplied trace
is evidence of the live schema and interpreter. Unsupported, structurally
different legacy table layouts report an explicit migration error instead of
being rebuilt with guessed data. See QUALITY_REVIEW_V3.5.3.txt for verification.
