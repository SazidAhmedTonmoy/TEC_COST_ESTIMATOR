TEC ConEst v3.5.3 — Confirmed startup repair and release verification
Prepared 21 October 2026

OUTCOME

The supplied production diagnostic (reference 84852851964d) identifies
sqlite3.OperationalError: no such column: deleted_at during opportunity index
creation. The delivered v3.5.2 code reproduced that exact exception against a
private fixture containing the current opportunity columns except deleted_at.

v3.5.3 now upgrades supported existing opportunity tables before creating the
dependent indexes. The repair is implemented and regression-tested locally.
No live hosting deployment or production data deletion was performed while
preparing the release. Production also needs the separately identified Python
3.9 Passenger configuration corrected to a supported application environment.

SCHEMA REPAIR

conest_app/opportunity_schema.py inspects PRAGMA table_info and safely adds
missing current columns to the supported id-primary-key/body-JSON layout.
Only newly added columns are recovered from JSON; existing SQL values, extra
columns and raw JSON documents are preserved. deleted_at is recovered from
deletedAt, so previously deleted records remain hidden.

Before migrating a populated legacy register, the application creates a
verified portable snapshot in the runtime Tender database's upgrade_backups
folder, with before-opportunity-schema-v353 in the filename. The backup is
private and checked for SQLite integrity and record count. It includes the
committed database state and is independent of WAL sidecars.

An OS lock serializes schema work across Passenger processes. BEGIN IMMEDIATE
excludes competing writers during the backup and migration. Schema changes,
backfill, related-table setup, index creation and defaults share one database
transaction using execute(), avoiding executescript() implicit commits. The
Store ready flag is set after successful commit. A failed backup commits no
opportunity changes; a later migration failure rolls those schema changes back.

Absent lookup tables can be recovered from the preserved opportunity JSON.
Existing assignment, activity and notification tables are retained. Recovery
does not invent approval history or past notifications. Known NSW/VIC region
defaults remain the configured origins, even when a project has a custom
distanceOrigin. Unsupported structural layouts fail with an explicit error
instead of rebuilding or discarding unknown data.

RUNTIME AND DEPLOYMENT

The supplied diagnostic shows /usr/bin/python3.9, Python 3.9.25, SQLite 3.34.1.
The missing-column error is a schema-upgrade failure. Python 3.9 is a separate
confirmed mismatch with the application's existing Python 3.10 minimum.
Python 3.11 is recommended here to match the workflow's configured CI version.

The installer requires recognizable or explicitly selected production Python
configuration. It no longer silently skips a broken configured path and uses
an unrelated command-line interpreter. It preserves a virtual environment's
interpreter path, including symlinks, and recognizes the documented literal
WSGI INTERP/os.execl startup pattern. Ambiguous runtime selection fails clearly.
The startup file is inspected as syntax and is never executed by the selector.

Python and its linked SQLite JSON/UPSERT support are checked before pip.
Required package imports and NSW/VIC timezones are checked after installation,
since installing tzdata can be necessary to provide the zones. CONEST_PYTHON
controls command-line tooling only; it does not reconfigure Passenger. The
restarted HTTP deep-health endpoint verifies the actual serving process.

The deployment workflow preserves the server's passenger_wsgi.py and .htaccess.
Instructions cover cPanel Setup Python App and the standard Application Manager
case, using the exact verified application environment rather than guessing a
virtualenv path. The repair requires no new dependency.
