IMPLEMENTED REPAIR

conest_app/opportunity_schema.py now supports an existing builder table with
name but no builder_key. It uses the existing OS process lock and a single
BEGIN IMMEDIATE transaction to:

1. Create a private, verified portable snapshot of the Tender database before
   changing the legacy directory. Builder counts are verified even when no
   opportunities table or opportunity rows exist.
2. Retain the entire original directory as opportunity_builders_legacy_v354,
   using a numbered suffix if that name is occupied. An earlier archive is
   never overwritten.
3. Create the current builder_key/name lookup and populate it using existing
   builder validation and normalization. A deterministic display spelling is
   retained for each normalized name. All original spellings and duplicates
   remain in the archive.
4. Leave invalid, blank, or nontext names in the archive without offering them
   as builder suggestions.
5. Preserve historical foreign keys, views, triggers, indexes, constraints,
   extra columns, and rows through SQLite's native rename behavior. Historical
   references follow the retained archive; new application writes use the
   current two-column lookup. The archive must remain in the database.
6. Verify that renaming did not change foreign-key integrity, allowing for
   SQLite's rewritten table names, including case differences.

The migration retains the previous missing-deleted_at repair and all supported
opportunity-column backfills. The complete transaction rolls back if backup,
renaming, integrity checks, later backfill, or index creation fails. The ready
flag is set only after successful initialization. A successful subsequent
startup uses the current directory without creating another migration archive
or importing archived names again.

The backup filename includes before-opportunity-schema-v354 and is stored in
the Tender database directory's upgrade_backups subdirectory. For the supplied
host configuration this is:
