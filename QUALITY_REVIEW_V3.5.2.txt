TEC ConEst v3.5.2 — Startup diagnostics verification
Prepared 21 October 2026

OUTCOME

The reported hosted error remains TENDERS_STARTUP_FAILED. The application did
not create stderr.log itself, and the host's actual Passenger log location is
unavailable. The new release privately captures future startup exceptions from
the actual failing process and lets an authenticated administrator retrieve
those records without starting Tender storage.

This is a diagnostic capability, not a claim that the unobserved production
root cause has been repaired. No live deployment or opportunity deletion was
performed while preparing this package.

NEW CAPTURE

conest_app/startup_diagnostics.py records the error reference/code, UTC time,
qualified exception class, message, chained traceback without local variables,
and limited Python/SQLite/release/PID/database-path information. It does not
connect to a database, initialize a store, dump request credentials, or dump all
environment variables. Explicit credential assignments and authorization
credentials are redacted from the saved text. Redaction is deliberately narrow;
an administrator should still review a diagnostic before sharing it elsewhere.

Storage is private to the application account in application-specific temporary
folders, outside detected web roots. Files use owner-only permissions and
atomic writes; process locking coordinates writers. Unsafe permissions,
symlinks, hard-linked records and web-root locations are rejected. Up to 32
records are retained across candidate directories, each at most 64 KiB, with a
seven-day maximum age. The host can clear temporary files earlier.

The public startup response still has its safe fixed message and reference.
It additionally reports diagnostics_available. Capture and logger exceptions
cannot replace or suppress the original safe error response. On unsupported
platforms without the POSIX privacy primitives, capture returns unavailable.

ADMINISTRATOR RETRIEVAL

GET /api/admin/startup-diagnostics
GET /api/admin/startup-diagnostics?reference=<12-lowercase-hex-characters>

The existing account session is required and the handler explicitly requires
the live role to be admin. The route executes before Tender initialization.
The endpoint returns one matching diagnostic or the latest retained record;
it cannot reconstruct references generated before capture was installed.

Responses are non-cacheable and do not enable cross-origin access. Missing
records return 404, malformed references 400, absent sessions 401 and ordinary
users 403. HEAD applies authorization and emits no response body. Mutation
requests never read diagnostics. Existing account status and password setup
requirements remain enforced.

  test_startup_diagnostic_http.py: 9 tests passed.

The capture tests include persistence across processes, four concurrent writer
processes, fallback after storage failure, complete storage failure, private
permissions, unsafe paths and links, reference validation, record byte/count/
expiry limits, explicit credential redaction and original safe public errors.

The real-WSGI HTTP tests include administrator/ordinary/anonymous sessions,
account deactivation and live role changes, password setup requirements,
latest/exact/missing references, malformed and duplicate references, HEAD and
mutation handling, non-cacheable responses, and preservation of sessions.

An integration case caused the Tender bootstrap to fail, captured its original
PermissionError privately, and retrieved that exact saved reference using only
the administrator session. Ordinary and anonymous requests received no trace,
private path, exception class or runtime details. The retrieval did not call
get_store, create the Tender database, or execute the opportunity reset.

Existing hosted-startup, deployment health, WSGI transport, Tender connection
lifetime and one-time reset tests passed. These are focused checks for this
release; the entire application test suite was not rerun.

The production Tender frontend build completed. Its compiled HTML/CSS/JavaScript
files were byte-identical to the previously delivered v3.5.1 build because this
update adds no visual frontend changes. No new Python dependency is required.

All database fixtures were isolated. The original supplied catalog remains
byte-identical to its uploaded source. Runtime databases, credentials and
captured diagnostic records are excluded from the release ZIPs. The packaged
blank Excel template is unchanged.

EXISTING OPPORTUNITY RESET

v3.5.2 introduces no new reset marker. The v3.5.1 owner-requested reset and its
verified backup behavior are retained. Reading the diagnostic endpoint does
not trigger it. Normal Tender initialization can still complete that earlier
reset if its existing completion marker has not yet been committed.

NEXT HOSTED STEP

Install the full package or overlay changed/new files onto the delivered
v3.5.1, restart the existing Passenger application, sign in as an administrator,
then open Tenders and Retry once. Open the administrator diagnostic URL in the
same browser and provide the captured exception and traceback for the exact
production fix. The diagnostic response's success:true means it read a record;
it does not mean Tender startup succeeded.

The current deployment workflow does not roll back uploaded files when its
later health verification fails. A remaining health error may therefore coexist
with the newly installed diagnostic capability. Check the captured runtime
release is 3.5.2. Read UPDATE_INSTRUCTIONS_V3.5.2.txt for full instructions.
